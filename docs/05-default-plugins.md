# 05 - Default plugins

The seven plugins that ship with IED. They are ordinary plugins (`docs/02`) of kind `builtin` - compiled into the server because C4 has no DLLs - using the same manifest, contribution points and bindings as anyone else; nothing about them is special-cased in the host, and each can be disabled. Full feature lists live in `docs/features/`; this doc gives each plugin's role, what it owns, and how it composes with the others.

| Plugin | Sidebar | Owns | Feature file |
|---|---|---|---|
| `ied.chat` | 1st (top) | chat UI, Mission Control, approvals, scratchpad, tasks, default AI tool bindings | `features/07-chat.md`, `features/16-orchestration.md` |
| `ied.editor` | 2nd | Monaco, Solution Explorer, document well, toolbar, Output, Error List, Find, Test Explorer, debugger windows, viewers, inline AI | `features/04-editor.md`, `05-build-run-test.md`, `06-debugger.md` |
| `ied.git` | 3rd | Fork/GitKraken-class source control | `features/09-git.md` |
| `ied.terminal` | none (bottom dock) | always-present terminal, AI terminals | `features/10-terminal.md` |
| `ied.sandbox` | plugin order | Docker/WSL/SSH sandboxes, sandbox terminals, AI sandbox tools | `features/11-sandbox.md` |
| `ied.profiler` | plugin order | capture library, timeline, analysis views, AI profiler tools | `features/12-profiler.md`, `docs/16` |
| `ied.gpu` | plugin order (after profiler) | GPU capture library, frame debugger views, replay backends (separate native processes), insights, compare, AI GPU tools | `features/17-gpu-debugger.md`, `docs/22` |

Host modules they sit on (not plugins): `src/fs` (documents, search), `src/tasks`, `src/lsp`, `src/dap`, `src/sandbox`, `src/profiler`, `src/spell` - the host's concepts, offered to plugins through the API (`docs/26` "Built-ins on the API"). Git's, the terminal's and the chat's server sides are their plugins' `code/`.

## chat

The first sidebar icon. Browser-like chat tabs, dockable side by side; streaming thinking/text/tool calls with per-segment timing and tokens; tool cards with status and elapsed time; stop reasons and harness notes always visible; chat bar with model group, effort, mode, permission mode, privacy lock, token totals, tokens/s and context fill; approval and question cards answerable from any device; collapsible right panel (context usage, modified files, tool stats, tasks, scratchpad, sub-agents, run info); scratchpad and task list; history search, fork, rewind; generic (no-project) chats. **Mission Control** (all runs across workspaces + the attention queue) and the goal board are part of this plugin.

Bindings provided: `chat.inject`, `chat.openTab`, `chat.attach { chatId, items }`, `chat.getActiveContext`, `orc.createGoal`. Consumes: `editor.openFile`, `editor.showDiff`, `terminal.run`.

**As built (M4, first slice):** `plugins/chat` declares the `ai.*` settings (`docs/04` "As built") and contributes the Chat activity (first in the sidebar and the phone's bottom bar), the status bar's "AI: 1 running, 1 needs you" and `ied.chat.show` (Ctrl+Alt+I), `ied.chat.new` (Ctrl+Alt+N), `ied.chat.stop`. The activity: a tab per chat of the workspace (chips on a phone; a tab closed on one device stays a chat, in All chats), the transcript (thinking folded, Markdown replies, tool cards that open to their result or diff, approval cards with Allow once / Allow for this chat / Always allow / Deny with message and Alt+A / Alt+D, the ask_user card, harness notes, each turn's stop, recoveries, tokens and speed), the composer (Enter sends - into a running turn at its next step, `docs/12` "Messages while a turn runs" - Ctrl+Enter queues for the next turn, Esc stops; `@` mentions a file, folder, `#symbol`, terminal, output, chat, `problems` or `diff` from a list above the box; files attached by the paper clip, a paste or a drop show as chips; group, effort (the group's named until the chat picks one, `docs/04` "Effort"), mode and permission, a row that scrolls at phone width; tokens, speed, time to first token, context use; `docs/04` "Attachments and @-mentions") and the right panel (context by part, tasks, modified files that open in the editor; long lists show `ai.chats.panelRows` rows until Show all, and its edge drags its width). It also draws Settings > AI > Models (profiles, Test connection) and Model Groups (the roles table, roles on and off) as `settingsPages`. Claude (2026-10-22, `docs/04` "The Claude Code provider"): Settings > AI > Claude (the CLI and whether it is on the Claude subscription, the plan's windows with their pace and resets, pacing's pick, Add Claude models), the status bar's "Claude 5h 42% wk 61%" opening it (`ied.chat.claudeUsage`, Chat: Claude Usage), and the composer's Model menu (a model pinned over the group's). Not yet: effort and the privacy lock, the scratchpad, sub-agents, Mission Control.

## editor

The Visual Studio heart of IED: Monaco on server-owned buffers; LSP features through profiles contributed by language plugins; Solution Explorer; preview tabs and splits including bound header/source splits; map-mode scrollbar; track-changes margin; find/replace in file, project, solution, federation; Output window with source dropdown and ANSI colors; Error List merging build, LSP and spell diagnostics; toolbar rendered from project tasks; Test Explorer; VS debugger windows over the host DAP pool; markdown preview with interactive checkboxes; image/video/hex and plugin viewers; browser pane; code-aware spell check UI; inline AI (Ctrl+I) and AI actions on menus and lightbulbs; ghost-text completion.

Bindings provided (largest surface in IED): `editor.openFile`, `editor.getSelection`, `editor.applyEdit`, `editor.showDiff`, `editor.revealProblem`, `tasks.run` (UI side), `editor.getOutput`; plus AI tools for symbol navigation that wrap LSP requests (`docs/13`).

## git

Sidebar icon under the editor. Commit graph, branches/remotes/tags/stashes/submodules/worktrees, commit details with diffs, file history and blame, staging by file/hunk/line, commit composer with AI-drafted messages, fetch/pull/push, merge/rebase (interactive) /cherry-pick/revert/reset, 3-way conflict resolution with optional AI help, LFS. Backend: the **git CLI** (`docs/99` #14). Worktrees also power agent isolation (`features/16-orchestration.md`).

**As built (M5, mockup 05):** the server side (`plugins/git/code/`, compiled into the server, on the plugin API since P4) and the protocol are `docs/10` "Git"; the plugin is `plugins/git` (settings `git.path`, `git.scanDepth`, `git.pullMode` on Settings > Source Control). The activity: a toolbar (the repository when there are several, Fetch, Pull with its modes, Push with the count to push, Branch, Stash, search by message, author, email or hash), the running operation's strip (its last line and percentage), the refs pane (local branches with ahead/behind, remotes, tags, stashes, worktrees, submodules; filter; click shows the commit, double click checks out, a context menu for checkout, new branch, rename, delete, apply/pop/drop), the commit graph (lanes laid out in the browser from the parents, labels for HEAD, branches, remote branches, tags and branches in other worktrees, virtualized, paged 200 at a time, a dashed "Local changes" row on top), and below it a commit's details (hash with copy, author, committer, parents, the branches it is on, the message, changed files with counts) or the local changes (conflicts, unstaged and untracked, staged; stage, unstage and discard per file or all) with the commit composer (summary length, Amend loads the last message, Ctrl+Enter), beside the chosen file's diff (inline or side by side, this device's choice; in the editor's syntax colors through the editor plugin's `editor.colorize` client binding, `docs/02`; in local changes Stage / Unstage / Discard per hunk and a click or Shift+click to pick lines; an untracked file shown whole; Open file). A checkout that would overwrite local changes offers to stash them first; deleting an unmerged branch asks again. The status bar shows the branch with what is to push and pull. On a phone: the graph alone with chips for the local changes, what is to push and the actions; a commit or the changes open over it with Back. Its server binding `git.workingDiff` gives another plugin the workspace's working-tree changes against HEAD as one text (the chat's `@diff` mention).

The AI's git tools (`docs/13` "git", 2026-10-22): `git_status`, `git_diff` (hunks numbered), `git_log`, `git_show`, `git_blame`, `git_branches`, and with the owner's approval `git_stage` / `git_unstage` (files or hunks), `git_commit` (what is staged, or named paths), `git_branch` and `git_stash`, through the plugin's `git.query` binding; none pushes.

Not yet: file history and blame in the activity, merge / rebase / cherry-pick / revert / reset, conflicts with the 3-way editor, AI commit messages, credential prompts in the UI, LFS, semantic (language server) colors in the diff.

## terminal

Not a sidebar tab: an always-present, collapsible shell docked at the bottom across all activities, full width minus the sidebar. ConPTY sessions that outlive the browser with server-side scrollback; profiles (PowerShell, pwsh, cmd, Git Bash, WSL, sandbox shells); multiple instances and splits; links and shell integration. The same supervisor runs task processes and the AI's shell commands - each chat gets a visible "AI: <chat>" terminal, so the owner sees exactly what the AI ran.

**As built (M3):** `plugins/terminal` contributes the `panels` view (`docs/02`) over the server's terminals (`docs/10` "Terminals", the plugin's own server code `plugins/terminal/code/`, compiled into the server on the plugin API): a tab per terminal of the workspace (`terms:<wsId>`, so every window lists the same; double-click renames in place; a context menu renames or kills), New (Ctrl+Shift+`), Kill, show/hide (Ctrl+`), Open in Terminal on a folder in Solution Explorer; xterm.js in the theme's ANSI colors, the screen rebuilt from the server's scrollback; a window that does not hold the lease watches, with Type Here. On a phone the panel is a slide-up drawer from More with Esc, Tab, Ctrl+C and the arrows. Its server binding `terminal.text` gives another plugin a terminal's last lines as plain text (the chat's `@terminal:` mentions). Not yet: splits, links, shell integration, the AI's terminals (M4).

### Terminal profiles

Owner (2026-10-26, list item 5): "dedicated python shell using the vendored python install". A **terminal profile** is a kind of terminal: a program with its arguments, environment and folder. Plugins contribute them (`terminalProfiles`, `shared/host-api/schemas/plugin-manifest.v1.schema.json`): `{id, title, icon, argv, env, cwd, when}`, whose strings take the variables of `docs/24` "Profiles and selection" - `${pluginDir}`, `${pluginState}` (the plugin's state folder, `<data>/plugins/<id>`), `${iedHome}` (the install, or the source a server runs from), `${workspaceDir}`, `${env:NAME}`, `${config:<key>}` and `${tool:<id>}` (`docs/26` "Language tools"). Of two with one id the last loaded plugin's wins. The terminal plugin knows profiles, never a language: the shells are its own profiles like any plugin's.

- **The terminal's own:** PowerShell (`pwsh -NoLogo`), Windows PowerShell, Command Prompt (`${env:ComSpec}`) and Git Bash (`${env:ProgramFiles}/Git/bin/bash.exe --login -i`), listed first, then the other plugins' in their load order.
- **The Python plugin's Python** (`plugins/python`): IED's own Python - the embeddable CPython 3.12 in `vendor/python` that runs SearXNG and web fetch (`docs/21`) - as `python -i shell/startup.py <pluginState>/packages`, in the workspace's folder. The embeddable build's `python312._pth` fixes `sys.path` (`python312.zip` and its own folder), turns `site` on, and puts Python in isolated mode, so `PYTHONPATH`, `PYTHONSTARTUP` and the other `PYTHON*` variables are ignored and the script's folder is not added. `startup.py` therefore gives the prompt what an ordinary `python` prompt has - the current folder (the workspace's) first on `sys.path` - and a place for packages: `<data>/plugins/ied.python/packages` (`%LOCALAPPDATA%\IED\plugins\ied.python\packages`), a site folder (its `.pth` files work) that nothing else uses - never IED's install (read-only at runtime) and never another Python's user site. `pip("install requests")` runs the pip that setup puts in `vendor/pip` (the install copies it beside `vendor/python`) as `pip install --target <packages>`; `pip("list")`, `pip("show requests")` and `pip("uninstall -y requests")` work too, and `pip` alone says how. Typing `pip install requests` at the prompt is Python, not a shell command - a `SyntaxError` - and the prompt says to call `pip()` instead. Everything the script defines lives inside a function, so the prompt starts with only `pip` beside Python's own names. `exit()` (or Ctrl+Z, Enter) ends the terminal.
- **Which runs:** New Terminal (the "+" and Ctrl+Shift+`) runs `terminal.defaultProfile` (a profile's id) when that profile can start, else the program `terminal.shell` names (the setting before profiles; empty by default), else the first of PowerShell 7, Windows PowerShell and the Command Prompt that is there. A profile can start when its program is found (a path, or a name on `PATH` with `PATHEXT`'s endings) and its folder exists; one that cannot is listed, greyed, with why.
- **The dock:** the chevron beside "+" (New Terminal with Profile) opens a menu of the profiles - icon and title, the default marked "Default", one that cannot start greyed "(not found)" - and a Default Profile submenu (Automatic, then each that can start, the setting's checked) that writes `terminal.defaultProfile` in the User tier. Each profile is also a command, "Terminal: New Python Terminal" (`ied.terminal.new.<id>`), and "New Terminal with Profile..." and "Select Default Profile..." open the menus from the palette. A terminal's tab shows its profile's icon. On a phone the menus are bottom sheets.
- **On the wire:** `term.profiles {wsId}` answers `{profiles: [{id, title, icon, plugin, available, problem}], default, setting}`; `term.create` takes `profile` (an unknown one is `not_found`, one that cannot start `unavailable` with why) and runs the default when given neither `profile` nor `argv`; a terminal's summary names its `profile` (empty for a program given as it is). A profile's terminal gets its `env`, the tools PATH (`docs/26` "Language tools") and `TERM_PROGRAM=IED`; `cwd` given to `term.create` (Open in Terminal) wins over the profile's.
- **Tests:** server checks `test_terminal_profiles.py` (the profiles and the default, a Python terminal answering `6*7` in the workspace's folder, `pip()` installing a wheel made on the spot into the packages folder and the module importing, a project plugin's profile with its variables, refusals); unit `frontend/tests/terminalprofiles.test.js`; e2e `terminal_profiles` (desktop and phone, mock and real).

## sandbox

Providers: Docker (Linux images), WSL, SSH (a Mac for macOS work, an ARM Linux box, any build machine) - Docker cannot legitimately run macOS on PC hardware, so "other OS" is generalized. Per-project sandbox definitions in `.ied/sandbox/`, solution bind-mounted, deny-by-default egress with grants, approved setup scripts, task targets (`target: sandbox:<name>`), container-to-host path mapping for errors, AI tools to run/build/test inside autonomously. Degrades with clear guidance when Docker is absent. For C4 projects it becomes fully useful once C4 targets Linux (`docs/17`, P-7).

## profiler

Tracy-class profiler built on the ITP trace protocol (`docs/16`). Tracy itself is a **feature reference only** - never linked into IED or C4. Timeline with frames, zones, plots, messages, locks; **thread renames as a time series with tinted segments and a by-task view**; statistics, find-zone, flame graph, compare; memory (live allocations, leaks by call stack, pools, GC events); GPU lanes with calibration (D3D12 first); capture library; Chrome-trace import (Nuke build traces, game-engine profiles); AI query tools. Instrumentation comes from Bedrock `Profile::` (`C4/Bedrock/`) so C4 programs are profileable by default.


**As built (2026-10-21, `docs/16` "As built"):** `plugins/profiler` - its server code in `code/` (the ITP listener with per-workspace tokens, live captures streamed to `.ied/local/captures`, the in-memory index, the `prof.*` methods, Chrome trace and pprof import, the `profiler.query` binding behind the `profile_*` AI tools) and its UI in `ui/` (the Profiler activity: Captures, and each capture a document with the frame graph, the canvas timeline by thread or by task with rename tints and each thread's lock rows, notes on the timeline, zone and lock details, Statistics, Find Zone, Messages, Memory, Flame Graph, Locks and Notes; Ask AI; the status bar's Capturing; desktop and phone; the AI's investigation tools - diagnose, hitches, threads, a zone, a window, allocations, leaks, memory over time, counters). Debug > Start Profiling (Alt+F2) runs the Profile task (`profile` slot; the `nuke`, `go` and `rust.cargo` presets' run the program with `IED_PROFILER=${profiler.connect}`). Clients: Bedrock `Profile::`, C and C++ (`Itp.h`), Go and Rust in their language plugins (`plugins/go/profiler`, `plugins/rust/profiler`); a language plugin's `profilerImporters` command converts its tool's traces (the go plugin's Go execution traces). Settings: `profiler.port`, `profiler.targetFps`, `profiler.followLive`. Not yet: GPU zones from Bedrock, captures larger than memory.
## gpu

PIX/RenderDoc/Nsight-class graphics debugger (`docs/22`). Capture library with build and commit metadata; Event Browser with GPU timing columns; Pipeline State with bindless resolution; Texture Viewer with browser-side display transforms and backend overlays; Mesh Viewer; Resources; Pixel History; Shader Debugger in an editor surface with Edit and Replay; Performance (timing, queue timeline, counter providers, insights); capture compare. Replay runs in a separate native backend process per capture (`rdc` over RenderDoc's C++ replay API first; IED's own Flashbang later), so a driver crash never takes the server down and no Python is involved.

Bindings provided: `gpu.captureFrame`, `gpu.openEvent`, `gpu.attachToChat`. Consumes: `editor.openFile`, `editor.applyEdit`, `tasks.run`, `profiler.openZone`, `chat.attach`.

## Language plugins

Declarative plugins (`docs/02`) that ship with IED and bring languages through the host's generic pools, so nothing about a language lives in the host:

- `ied.languages`: ids, extensions, comment tokens and brackets for common languages, and C/C++ header/source pairs, so every document has a language (Monaco's tokenizers color them) before a dedicated plugin adds more.
- `ied.cpp` (C/C++): clangd as the language server of `c` and `cpp` documents (one per workspace; `cpp.clangd.arguments`; `cpp.languageServer` turns it off). clangd and CodeLLDB ship with IED inside the plugin's install folder (`docs/21`, `docs/26` "Language tools": its `clangd` and `codelldb` tools, `bundled` first); `cpp.clangd.path` and `cpp.lldb.path` (empty by default) name others. clangd finds each file's flags in the nearest `compile_commands.json` (or `compile_flags.txt`) above it or in a `build/` folder beside one - what CMake and most build systems write - and guesses without one. Debugging through LLDB with CodeLLDB's adapter (`${tool:codelldb}`), adapter type `lldb` in a project's `debug` configurations (`docs/25`); it debugs Rust too.
- `ied.rust` (Rust): rust-analyzer as the language server of `rust` documents (`${tool:rust-analyzer}`: rustup's for the workspace's toolchain, or `rust.analyzer.path`); its tools `rustup`, `cargo` and `rust-analyzer` (`docs/26` "Language tools": asked in the workspace's folder, so rustup answers for the toolchain `rust-toolchain.toml` pins; installed for the user, asked first, through rustup-init, `rustup toolchain install` and `rustup component add`); the `rust.cargo` task preset for a folder with a `Cargo.toml` (a Debug / Release profile; Build, Run, Test and Clean running `${tool:cargo}`) with the `rustc` problem matcher over cargo's `--message-format=short`; and a `Launch` configuration that debugs `target/<profile>/<project>.exe` through `ied.cpp`'s CodeLLDB after the build; a Profile task (`cargo run` with `IED_PROFILER`) and the `ied-profiler` crate (`plugins/rust/profiler`, `docs/16` "Clients"). Checked live: rust-analyzer running, a type error at its line in the Error List, a breakpoint stopping with its locals.
- `ied.go` (Go): gopls (`${tool:gopls}`), Delve as the debugger (adapter type `go`: `dlv dap --client-addr=127.0.0.1:${port}`, Delve's DAP mode dialing IED's port, `docs/25`; the `go` preset's Launch - `mode: debug` of the project's folder - and Test configurations, `go.nuke`'s Launch of the program Nuke builds, `mode: exec`), and its tools `go`, `gopls` and `dlv` (`docs/26` "Language tools": go.mod's `toolchain`, else `go` line as the minimum; Go from go.dev's archive, gopls and Delve by `go install` of a pinned version into IED's tools folder). Settings `go.path`, `go.gopls.path`, `go.delve.path` (empty: automatic).
- `ied.python` (Python): icons, traceback links and the Python terminal profile above.
- One plugin per further language as its server is wired (the web languages): a profile that runs the language's usual server, its program a `tools` entry.

A language server or debug adapter whose tool is missing does not start: `lsp.status` (or the session) fails at once with "gopls is not installed: ... Settings > Languages installs it." and the language keeps its basic support; the workspace's banner names what is missing (`docs/26` "Language tools").

## Cross-plugin notes

- Every plugin exposes its useful capabilities as **skills** (how to use them) and, where actionable, **AI tools** and **bindings**.
- Default sidebar order: workspace switcher, chat, editor, git, then plugin activities by `order`; notifications and settings at the bottom.
- Minimal configuration: IED must remain usable with only `ied.editor` and `ied.terminal` enabled (documented and tested).
